## 1. 项目目的与优先级

建设一个能长期用于个人学习与资料查找的知识库 RAG：资料存得进，问题找得到依据，回答帮助理解，学习成果能保存与复用。

第一目标是真实个人使用价值与良好的使用体验。实现时适度考虑简历和面试，保留需求、设计取舍、失败分析和效果证据；求职展示来自实际成果，不单独驱动功能建设。

首个重点场景是阅读技术书籍和论文，当前以 AI-Infra-Book.pdf 为主要验证资料。中文为主，兼顾英文技术术语；更广的资料类型和跨文档能力需要另行验证，不能由单本文档成绩推定。

用户已明确的约束：

- 先完成整体项目闭环，再围绕实际需求深化学习体验。
- 基本可用性、响应反馈、来源核对、异常恢复，本身就是闭环验收的一部分。
- 暂不投入注册、多租户、复杂权限等企业化体系；保持个人本地使用范围。
- 遇到具体问题并取得证据后才考虑更强的检索手段；BM25、HyDE、模型替换等没有默认实施承诺。
- 优先把现有功能用好，不以功能数量、技术栈数量衡量进度。

## 2. 要解决的实际问题

| 用户任务 | 当前要提供的价值 | 如何确认价值 |
| --- | --- | --- |
| 读书遇到陌生概念、缩写 | 快速找到定义或机制正文，得到可核对的解释 | 从真实阅读中选题，检查解释与原文一致、来源能定位 |
| 理解两个概念的区别或关系 | 分别回答核心问题，指出资料无法支持的部分 | 逐项检查问题是否被回答，避免相关片段被当成充分证据 |
| 阅读长资料时定位内容 | 减少反复搜索、翻页和拼接上下文 | 记录一次正常查阅和一次工具辅助查阅的步骤、耗时与困难 |
| 保存自己的理解并再次使用 | 问答可整理为可编辑笔记，日后能找回并核对来源 | 间隔使用时实际找回一条笔记和对应依据 |
| 长期积累、更新资料 | 更新、删除、重启和恢复后，资料状态与答案来源仍可解释 | 使用受控样本演练更新失败、恢复和旧引用查看 |

时间节省、满意度等数值必须实测。初期记录真实阅读任务即可，不预设未经验证的“效率提升百分比”。

## 4. 总路线与阶段退出条件

按 A → B → C → D → E 推进。各阶段只细化当前需要实施的范围；下列验收条件是路线目标，尚未完成的不能登记为成果。真实使用中的阻断问题可随时优先处理。

### A. 可信问答与质量闭环（当前）

用户价值：能够理解回答依据，知道哪些能回答、哪些缺资料，并能稳定复现与修正错误。

主要工作：

1. 统一四个概念：两路候选、融合后选中片段、充分度判定后送入生成的证据、生成答案实际引用的证据。
2. 修正评测口径，分开衡量检索效果、证据判定效果和回答质量。无答案题允许检索到近邻，不能仅因存在候选就判系统回答失败。
3. 核对题集的核心子问题、支持证据和预期状态；充分、部分、不足均需覆盖。固定回归题与新增真实问题分开记录，避免只为已知题目调整规则。
4. 补齐 partial 的回答约束、缺失内容展示与历史保存，核验当前拒答规则的误拒与误放。
5. 运行全题集并人工检查真实答案，形成“失败定位 → 修复 → 回归 → 用户复测”的流程。

退出证据：

- 保存带提交、资料哈希、模型、配置、时间和指标定义的可重复评测报告。
- q04 同时回答预填充与解码，具有正文依据；q23–q25 正确拒答，不将无关数字或术语当作充分支持。
- 校准后的可回答题逐题核对错误拒答、缺失子问题与引用支撑；未覆盖的范围明确列出。
- partial 用例只回答有依据部分并明确缺失部分，重新打开历史后信息仍一致。
- 前端诊断与报告能追踪候选到最终答案的证据变化。
- 至少完成一次真实阅读任务的完整使用记录；测试数与页码命中率不代替答案验收。

现有 25 题作为起点，不把之前提出的“20 道正例全部通过”直接当成已经核实的题集分组或完成指标；分母需由校准结果明确。

### B. 可诊断、可恢复的日常使用

用户价值：知道系统正在做什么；等待、失败或取消后有明确出路，维护者能定位问题。

主要工作：

- 为请求串联解析、召回、融合、重排、判定和生成的必要诊断信息，记录耗时、错误阶段及回退原因。
- 默认日志不记录密钥与完整私人正文，必要诊断控制内容范围。
- 明确上传等待、模型不可用、取消、重复提交等状态，保留可恢复的数据。
- 根据实测发现的响应瓶颈优化；先记录首响应、首 token、完成耗时和失败类型，再定性能目标。

退出证据：受控故障能定位到阶段；用户能取消、重试或恢复；一次请求的主要耗时可追踪；真实使用反馈无未处理的阻断问题。优先使用轻量日志和现有诊断界面，是否引入独立监控服务由需要决定。

### C. 文档生命周期与个人数据安全

用户价值：资料长期积累后仍敢更新、删除与迁移，旧笔记来源可解释。

主要工作：

- 设计可识别的文档版本和安全更新流程；处理失败时避免丢失上一份可用资料。
- 明确新旧索引切换及旧回答、旧笔记引用的版本含义。
- 完善备份、恢复和可携带导出；说明备份中的密钥保护和删除边界。

退出证据：更新成功、更新失败、删除、重启、备份恢复均有受控验证；新问答不混用失效资料，旧引用的版本或失效状态可见；用户能依照说明恢复自己的资料。

### D. 可复现安装、升级与交付

用户价值：换一台机器仍能安装使用，更新程序不会依赖开发者临时手工操作。

主要工作：

- 完善安装、配置、启动、升级、备份和恢复说明，展示运行版本，减少“代码已合并但运行的还是旧版本”的混淆。
- 建立 CI，运行确定性测试、构建与评测结构检查；私人语料和付费生成评测不直接放入公共 CI。
- 验证容器化交付的适用性，并提供 Docker/Compose 方式；保持 Windows 本地启动路径可用，明确模型缓存与数据持久化要求。
- 记录机器、依赖与数据规模下的实际表现。

退出证据：在干净环境按文档完成安装与一次问答；CI 运行记录可查；一次升级和数据恢复演练可复现。部署方式以便于个人实际使用为标准。

### E. 基于真实需求深化学习体验

进入条件：A–D 的基础闭环已有验收证据；当前链路的基础体验问题不需要等到本阶段才修。

从真实使用记录选择最值得做的一项，例如：

- 原文阅读、上下文展开与来源跳转。
- 笔记检索、整理、导出及再次利用。
- 跨资料比较与明确来源归属。
- 确有复习需求时，再做概念卡片、练习题或复习提醒。

每项都先记录“用户在什么任务中遇到什么困难”，以完整任务前后对比验收。上述是候选方向，不是必须全部交付的功能清单。

## 5. 排序与范围控制

新增工作按以下顺序处理：

1. 资料丢失、泄露、明显误导、无法完成核心任务。
2. 当前阶段的质量与恢复缺口。
3. 真实使用反复出现的操作成本与理解困难。
4. 有明确收益证据的能力拓展。

提出任何新技术或功能，记录需求、可复现问题、当前做法的不足、最小方案和验收证据。没有具体漏召回案例时，不启动 BM25、HyDE 或更多检索管线；没有实际规模压力时，不启动向量数据库迁移或分布式改造。

当前主线不包含：账号注册、多租户、复杂权限、多人协作、公共网络部署、知识图谱、自动联网研究。将来若使用范围发生变化，先更新需求与边界。

本地优先的含义：资料和索引本地保存，默认向量模型本地运行；使用云端回答服务时，问题与检索片段仍可能发往配置的服务。不能宣传为“所有内容完全不外发”。

## 7. 跨会话接续与文档维护

文档分工：

- 本文：项目方向、当前状态、阶段验收与下一步的主要入口。
- [mvp-progress.md](mvp-progress.md)：保留最初 MVP 历史记录，并追加后续重大交付的摘要与证据入口。
- [原项目计划书](personal-knowledge-base-plan.md)：保留历史设想；与本文冲突的路线、顺序和边界以本文及用户最新明确指示为准。
- docs/superpowers/specs/ 与 plans/：单项功能的详细设计和执行计划，不代替全项目状态。
- docs/evaluations/：题集、评分说明与可公开的结果摘要；test-results/ 保存本机原始报告，不提交私人语料与密钥。

新会话开始：

1. 先读本文和执行记录，确认当前阶段及下一项。
2. 检查当前分支、提交和工作区修改；涉及在线行为时核对运行版本、启动方式和数据范围。
3. 查阅本次工作相关的设计和证据；历史报告只代表对应提交与配置。
4. 遵循用户最新指示推进，不凭旧聊天总结把规划视为已完成。

完成工作时，同步记录状态、提交/文件、验证命令及结果、未解决项、下一步和是否需要构建/重启。区分“代码已实现”“自动测试通过”“真实资料验证通过”“用户使用验证通过”；缺少后两者时不能声称整体效果达标。

更改定位、阶段顺序或引入较大能力时，把用户决定及原因写入决策记录；日常修复不重复启动项目总路线讨论。
