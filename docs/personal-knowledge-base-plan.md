# 个人知识库项目计划书

日期：2026-09-19  
版本：v0.2，按用户反馈调整为 Chroma 验证阶段与 RAG 优先  
项目目录：`D:\rag`

## 一、项目定位

建设一个面向个人学习与工作的知识库，将分散的笔记、学习材料和工作文档集中保存，支持关键词搜索、语义搜索，以及能够回到原文核对的 AI 问答。

核心目标：**资料存得进、内容找得到、回答有依据、数据带得走。**

用户已确认：面向学习与工作资料，用户上传后由系统自动解析、切分、向量化和检索，再利用相关资料辅助回答问题；初期使用 Chroma，后期考虑 PostgreSQL + pgvector。

首版核心流程：**用户上传 → 自动处理 → 建立索引 → 用户提问 → 检索相关片段 → AI 根据片段回答并展示来源。** 这不是训练或微调模型，也不需要先准备固定数量的资料。上传一份受支持的文档即可开始处理和问答。

以下内容仍为建议假设：

- 单人使用，中文内容为主，兼顾英文技术资料。
- 首版为桌面浏览器 Web 应用，默认在个人电脑本地运行。
- 验证阶段从 1 份文档跑通流程，再用约 5～20 份不同类型资料检查质量；这些仅为开发测试样本，不是使用门槛或上传上限。
- 原计划的 100～500 份及 5,000 份／100,000 片段只是测试规模设想，现已撤销首阶段的大规模容量测试要求。文档数量和片段数量没有固定换算关系，取决于文档长度与切分策略；后续根据实际使用规模安排压力测试。
- 原文件和持久化数据保存在本机；外部 AI 服务可配置，未配置时仍可上传、查看资料；依赖模型的向量化与问答显示等待配置状态。
- 本期交付计划书；开发时根据实际资料和机器条件细化依赖版本、模型和性能预算。

## 二、建设路线比较

| 路线 | 优点 | 代价与适用条件 |
| --- | --- | --- |
| 先完善文档管理，再加入 AI 问答 | 先建立资料整理能力 | 会推迟当前最关心的 RAG 验证 |
| RAG 闭环优先（采用） | 尽早验证上传、自动处理、检索与有依据的回答 | 首阶段只保留必要的文档列表、状态和来源预览，后续补充整理功能 |
| 完全离线的本地 AI 知识库 | 可减少向外部服务发送内容 | 模型部署、硬件占用与推理速度需要单独验证 |

采用第二条路线：先实现端到端文档问答，再完善独立搜索和资料整理。向量存储与模型调用都封装为可替换接口。

## 三、典型使用场景

1. **学习回顾**：导入课程笔记和技术文档，提问“缓存为什么会失效”，系统自动检索相关段落并结合资料解释。
2. **工作查找**：输入“上次项目上线前检查了哪些事项”，从工作文档中检索，而不必记住文件名。
3. **跨文档整理**：选中几份方案，要求 AI 对比差异；每个关键结论都有对应来源。
4. **积累自己的理解（后续）**：将有价值的回答保存为 Markdown 笔记，保留引用，人工修改后再纳入知识库。

## 四、首版功能范围

### 4.1 必须完成的功能

| 模块 | 首版内容 | 完成标准 |
| --- | --- | --- |
| 资料导入 | 批量上传 Markdown、TXT、可提取文本的 PDF、DOCX；显示上传和处理状态 | 能从上传走到可搜索；失败有原因且可重试 |
| 文档管理 | 标题、所属知识库、处理状态、更新时间、原文件下载 | 支持列表、重新上传与删除 |
| 阅读与定位 | 原文件或提取正文预览、匹配片段定位 | PDF 可按页定位；其他格式按章节或段落定位，不虚构页码 |
| RAG 检索 | 提问时自动进行向量检索，限制在当前选定知识库或文档范围 | 能获取相关片段及来源；用户无需手动切分或搜索 |
| AI 问答 | 选择全部资料、某个知识库或指定文档提问；流式显示回答 | 关键结论可核对来源；证据不足明确说明 |
| 任务与异常 | 解析、索引进度，失败重试，模型超时和取消 | 页面不长时间无反馈；后台任务可恢复 |
| 数据持久化 | 保留原文件、元数据和 Chroma 索引，提供本地备份与恢复说明 | 重启后仍可问答；验证一次恢复 |
| 设置 | 模型连接、服务地址、索引状态、备份入口 | 密钥保留在后端，界面只展示脱敏信息 |

组织方式保持简单：每份文档属于一个知识库，后续再加入标签与收藏。当前按单人本地验证规划；若开放多个账号，必须增加身份认证与服务端用户数据隔离，检索范围不能仅由前端传入决定。

建议初始上传限制为单文件 20 MB、单批 20 个，实际限制由解析测试调整。扫描 PDF、加密 PDF、复杂表格和公式若无法可靠提取，明确显示受限或失败状态，不能显示为完整处理成功。

## 六、建议技术架构

### 6.1 技术分工

| 层级 | 建议方案 | 选择理由 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite | 与现有 React Router 项目约束保持一致，便于独立开发页面 |
| 路由与样式 | React Router 配置式路由、SCSS Modules | 满足用户指定的 config 路由与页面目录规范 |
| 后端 | Python + FastAPI | 将文件处理、检索和模型调用集中在服务端 |
| 向量存储 | Chroma，本地持久化 | 验证阶段保存片段、向量及检索所需元数据；后期考虑 PostgreSQL + pgvector |
| 业务数据 | SQLite（建议） | 保存文档状态、任务、会话和有效版本，避免将 Chroma 当作通用业务数据库 |
| 文件保存 | 本地持久目录 | 保留原始文件；数据库仅记录受控路径与校验信息 |
| 异步处理 | 独立 worker + 数据库任务表 | 上传请求快速返回，解析和索引任务可重试、恢复 |
| AI 接入 | 独立的 Embedding 与生成模型适配层 | 允许分别选择模型，并隔离不同服务商的接口差异 |
| 运行方式 | 本地前端、FastAPI 与单个处理 worker；Chroma 本地持久化、SQLite 文件存储 | 验证阶段无需部署 PostgreSQL；worker 负责 Chroma 读写，API 通过持久任务传递索引和查询请求，避免多个进程直接操作同一嵌入式存储目录 |

以上为拟采用方案，不代表已完成兼容性验证。第一阶段需验证 Windows 本地运行、中文检索、文档提取和模型连通性，再锁定版本。

Chroma 的 `PersistentClient` 支持将数据保存到本地目录，并在启动时加载，适合开发验证；需要并发服务时可先改为 Chroma 服务模式，不必因验证结束立即迁移数据库。[Chroma 官方客户端文档](https://docs.trychroma.com/docs/run-chroma/clients)

存储职责：原文件在文件目录；业务状态与规范化片段正文在 SQLite；Chroma 保存向量、供检索使用的片段副本及文档 ID、版本、定位等元数据。解析、切分由后端处理模块负责，Embedding 模型负责向量化，Chroma 负责向量存储与检索，生成模型负责组织回答。

保留 `upsertChunks`、`search`、`deleteDocument` 等向量存储接口。后期确有部署、并发或统一数据管理需求时，再实现 pgvector 适配器并迁移业务数据。迁移保留稳定文档与片段 ID、模型标识、向量维度和切分版本，回放同一问题集核对结果后再切换。需要时从保留正文重新生成向量；这不等于只改配置即可迁移。

React Router 官方支持将路由对象配置传入 `createBrowserRouter`，可用于落实项目的配置式路由要求。[官方路由文档](https://reactrouter.com/start/data/routing)

文件解析和批量向量计算使用独立 worker；FastAPI 的进程内后台任务不承担需要可靠恢复的处理队列。[FastAPI 后台任务说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)

### 6.2 前端目录约束

严格遵循已提供的项目规则：

- `src/app.tsx` 只负责路由配置，不编写页面业务逻辑；通过 config 路由对象组织页面。
- 所有页面位于 `src/pages/<PageName>/`，包含 `index.tsx`、`hooks/`、`style/`、`components/`。
- 每个页面内组件位于独立的 `components/<ComponentName>/`，包含 `index.tsx`、`hooks/`、`style/`。
- 页面状态与操作放在对应 hooks；页面级样式放在 `style/index.module.scss`。
- 跨页面 API 请求、类型和通用组件分别组织，避免页面之间相互引用内部组件。

示例目录以搜索页为例，其他页面遵循同样结构：

```text
src/
├─ app.tsx
├─ main.tsx
├─ services/
├─ types/
└─ pages/
   └─ Search/
      ├─ index.tsx
      ├─ hooks/useSearch.ts
      ├─ style/index.module.scss
      └─ components/
         └─ SearchResult/
            ├─ index.tsx
            ├─ hooks/useSearchResult.ts
            └─ style/index.module.scss
```

## 七、搜索与 AI 问答方案

### 7.1 导入流程

上传 → 校验格式与大小 → 保存原文件并计算内容哈希 → 创建处理任务 → 提取正文与定位信息 → 按章节、段落切分 → 调用 Embedding 模型生成向量 → 将片段、向量与元数据写入 Chroma → 发布可用索引版本并标记可问答。

同一知识库内发现相同哈希时提示复用已有文档，避免重复计算。片段必须保留文档 ID、版本、章节、页码或段落位置。

切分初始可尝试约 400～800 tokens、约 10%～15% 重叠，再根据真实资料评测调整；表格和代码块尽量保留结构，避免仅按长度机械截断。

### 7.2 检索流程

用户提问 → 确定可访问的知识库和文档范围 → 使用与文档相同的 Embedding 模型向量化问题 → 在 Chroma 检索相关片段 → 检查文档有效状态与版本 → 返回片段与来源。

初始检索可尝试返回 5～10 个片段，再根据上下文长度预算和评测结果调整。片段不足时不以无关内容补齐；相似度分数不是答案可信度，需要用有答案和无答案问题校准筛选策略。

中文关键词检索、混合召回与重排放到后续优化。在专业术语、编号等查询上发现向量召回不足后，用固定问题集验证新增能力的收益。

### 7.3 回答流程

问题与必要会话上下文 → 检索相关片段 → 在长度预算内组织证据 → 模型生成 → 校验引用 ID → 展示回答与引用卡片。

- 默认依据知识库内容回答，外部常识补充若未来开放，必须有清楚标记。
- 每条引用绑定真实文档版本和片段，点击后打开对应位置。
- 只允许使用本次检索提供的引用 ID；ID 校验不等于结论正确，还需评测回答是否被引用支持。
- 检索无结果或材料不足时，说明缺少哪些信息，避免强行生成结论。
- 资料存在冲突时列出不同来源与日期，不擅自判断哪份一定正确。
- 引入的文档内容作为资料处理，不允许覆盖系统规则或触发工具操作。
- 更换 Embedding 模型或向量维度时重建对应索引，不能将新旧向量直接混用。

### 7.4 更新与删除

重新上传以替换文档时生成新版本和新索引；新索引完成前继续使用完整旧版本并提示更新中。新版本完整写入 Chroma 后，切换 SQLite 中的有效版本指针；检索始终校验有效版本，随后清理旧片段。跨存储不假设存在原子事务，失败依靠任务重试与清理恢复。问答绑定实际使用的版本。

删除后立即从检索范围排除，异步清除原文件和索引；旧会话显示“来源已删除”并清理缓存引用摘录。历史回答和备份可能仍包含衍生内容，需提供会话删除与备份保留周期说明，不能将删文档描述为所有副本已消失。

## 八、核心数据模型

| 实体 | 主要信息 |
| --- | --- |
| KnowledgeBase | 名称、说明、创建时间 |
| Document | 所属知识库、标题、格式、当前版本、处理状态 |
| DocumentVersion | 内容哈希、原文件位置、提取正文、版本号、创建时间 |
| Chunk | 文档版本、正文、章节或页码、片段顺序、索引版本 |
| Embedding | 片段、模型标识、维度、向量 |
| Tag / DocumentTag（后续） | 标签与文档关联 |
| IngestionJob | 任务类型、阶段、重试次数、错误、worker 租约 |
| Conversation / Message | 问答范围、内容、时间、模型与用量 |
| Citation | 回答与文档版本、片段及定位信息的关联 |

任务应可重复执行而不生成重复片段。进程中断后可回收过期租约；文档已被删除时，旧任务不能重新发布索引。

## 九、数据边界与运行成本

默认仅监听本机。若后续开放局域网或公网，必须在该阶段加入认证、传输加密与访问限制。

本地保存不等于内容不会外发：云端 Embedding 会接收待向量化文本，云端生成模型会接收问题和检索片段。第一次启用外部服务时明确展示这一范围。未允许外发的资料仅保存与预览；除非配置合适的本地模型，否则不送入云端 RAG 链路。

上传采用受控存储路径与格式检查；渲染 Markdown 和提取内容时过滤可执行内容；API 密钥、全文和问题正文默认不写入普通运行日志。

备份覆盖原文件、SQLite、Chroma 持久目录、数据结构版本和必要配置；密钥单独保护。验证阶段停写后备份以保持一致，恢复后按模型配置检查是否需要重建向量索引。

月度运行成本由存储与备份、首次/增量 Embedding、问答输入输出、可选 OCR 与重排构成。模型服务商、用量和部署位置尚未确定，因此本计划不提供虚假的固定月费。开发中记录实际 token 用量，支持按文档增量索引、问答上下文上限和调用额度限制。

## 十、实施阶段与交付物

以下按一名熟悉相关技术的开发者估算，验证版约 9～15 个有效工作日，属于规划估算；不包含完整笔记系统、混合检索、OCR、多账号和 pgvector 迁移。原 18～26 天估算对应更宽的资料管理范围，不再作为当前验证版排期。

| 阶段 | 估算 | 交付物 | 阶段验收 |
| --- | --- | --- | --- |
| 1. 最小技术闭环 | 2～3 天 | 一份文档的解析、切分、Embedding、Chroma 检索与模型回答 | 能回答文档内的问题并给出真实片段来源 |
| 2. 上传与处理界面 | 2～4 天 | 项目骨架、上传列表、处理状态、持久任务、文档预览 | 用户上传后自动进入处理流程，失败可见且可重试 |
| 3. 问答界面 | 2～4 天 | 范围选择、流式回答、引用定位、基本会话 | 用户无需手动执行 RAG 步骤即可提问 |
| 4. 验证与交付 | 3～4 天 | 重复导入、更新删除、重启恢复、备份恢复、质量评测及运行说明 | 小样本端到端流程可重复运行，引用与数据状态一致 |

第一阶段就在技术链路上跑通回答，第三阶段形成用户可操作的完整界面。如果回答质量不达标，先检查解析、切分与召回，再调整生成模型。

## 十一、验收与质量标准

开发先用 1 份资料验证流程，再逐步积累约 5～20 份代表性资料、30 个可回答问题和 10 个无答案问题，覆盖跨文档查询、精确术语、重复导入、修改和删除。测试人员标记预期来源；普通用户无需准备测试集，也无需一次上传这么多资料。小样本结果仅用于发现问题，不能证明大规模质量与性能。

以下数字为拟定验收目标，实际结果需记录测试机器、数据规模、模型及网络环境：

| 指标 | 首版目标 |
| --- | --- |
| 支持格式的解析成功率 | 在有效样本中达到 95%，失败全部可见且有原因 |
| 来源召回 | 30 个可回答问题中，至少 85% 在前 5 条结果出现标注来源 |
| 引用定位 | 验收样本中的引用 ID 均能定位到对应版本，或明确标为来源已删除 |
| 回答依据 | 至少 90% 的抽查关键事实有引用且被对应片段支持 |
| 无答案处理 | 10 个无答案问题至少 9 个明确提示材料不足 |
| 检索延迟 | 记录实际文档数、片段数、硬件与检索耗时；先验证交互可用性，大规模压力测试后置 |
| AI 体验 | 提交后 1 秒内展示工作状态；首 token 与总耗时分别实测，超时可取消和重试 |
| 数据完整性 | 重复导入不重复建库；修改后无新旧索引混用；删除后不再被召回 |
| 灾难恢复 | 完成一次空环境恢复，抽检原文件、文档状态、会话与索引 |

自动化验证重点放在解析定位、过滤边界、索引版本切换、删除与任务并发、引用绑定和备份恢复。页面再进行完整流程检查，包括空数据、网络失败、模型限流和进程重启。

## 十二、主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 资料能上传但提取结果差 | 先用真实样本做解析验证；展示提取正文供核对 |
| 搜索召回弱导致回答错误 | 将解析、召回、生成分别评测；根据失败案例决定是否加入关键词混合检索 |
| 有引用但结论不受引用支持 | 做事实与证据人工核对，不能只检查引用链接存在 |
| 修改、删除后仍引用旧内容 | 文档与索引版本化，删除立即排除，异步任务检查有效状态 |
| 外部 AI 不可用或费用增加 | 保留原文件与处理进度，显示失败原因并允许重试；限制上下文和重复计算 |
| 范围持续扩大 | 以“导入—搜索—带引用问答—原文核对”作为首版边界 |

## 十三、建议的下一步

进入开发准备时，用一份可用于测试的资料和几个相关问题验证链路，并确定主要文件格式和模型配置。更多测试样本在开发过程中逐步补充，不作为开始开发的前提。

先以 Chroma 跑通“上传—自动解析与切分—向量化—检索—带来源的回答”，再完善资料管理和评估是否迁移 PostgreSQL + pgvector。
